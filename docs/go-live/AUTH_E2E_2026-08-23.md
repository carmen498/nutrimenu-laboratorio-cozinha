## 8. Token expirado

O e-mail real da Base44 informa explicitamente: **“Link expires in 1 hour”**.

O token recebido é opaco e não expõe uma claim JWT `exp`, portanto sua expiração não pode ser acelerada ou falsificada sem deixar de ser um teste real. Não foi esperado o período de uma hora apenas para produzir um falso “E2E imediato”.

Já estão comprovados:

- token inválido rejeitado;
- token usado rejeitado;
- interface atual trata mensagem de token inválido/expirado como link inválido.

Pendente literal: usar um token real após ultrapassar sua validade de 1 hora e confirmar a rejeição do servidor.

Status: AMARELO — comportamento estrutural correto, expiração temporal real ainda não executada.

## 9. Domínio do link de recuperação — achado e correção

O E2E revelou que o e-mail gerado pela autenticação nativa da Base44 aponta primeiro para:

`laborat-rio-de-cozinha.base44.app/reset-password`

O envio passa por click tracking do SendGrid antes desse destino.

Como o SDK `resetPasswordRequest(email)` não oferece parâmetro de redirect/custom reset URL, a correção foi implementada no bootstrap do frontend:

- se o navegador chegar a `/reset-password?token=...` no host exato `laborat-rio-de-cozinha.base44.app`;
- redireciona imediatamente para `https://laboratoriodecozinha.com.br/reset-password?token=...`;
- no domínio próprio, o token é guardado em `sessionStorage`;
- o parâmetro `token` é removido da barra antes de scripts externos;
- `ResetPassword.jsx` lê apenas o token protegido do `sessionStorage`.

O teste `scripts/test-auth-routing.mjs` protege essa ordem de operações.

Status do source: VERDE.
Status na build pública: PENDENTE PUBLICAÇÃO DA FASE 8.
