# Auditoria P0 — Row Level Security (RLS)

Data: 2026-08-22
Escopo: entidades Base44 do Laboratório de Cozinha

## Objetivo

Garantir que:

1. dados pessoais de um usuário não sejam lidos, alterados ou excluídos por outro usuário;
2. catálogos globais sejam legíveis pelos clientes, mas somente administradores possam alterá-los;
3. dados administrativos, logs e configurações não sejam expostos a usuários comuns;
4. entidades-filhas de receitas e cardápios respeitem a mesma propriedade da entidade-pai.

## Padrões adotados

### Dados pessoais

- create: usuário autenticado ou admin;
- read/update/delete: `created_by_id == {{user.id}}` ou admin.

### Catálogos globais

- read: liberado;
- create/update/delete: somente `role=admin`.

### Dados administrativos/logs

- read/create/update/delete: somente `role=admin`.

## P0 pendente — entidades-filhas mistas

As seguintes entidades não podem receber simplesmente `created_by_id == user.id`, porque armazenam tanto linhas pertencentes ao catálogo-base quanto linhas de cópias pessoais:

### Filhas de Receita

- `IngredienteReceita`
- `ReceitaTag`
- `InsumoReceita`
- `IngredienteEsquecidoReceita`

### Filhas de Cardápio

- `CardapioReceita`
- `CardapioInsumo`
- `CardapioTag`

O pai (`Receita`/`Cardapio`) já possui `is_base` e `usuario_dono_id`, mas as linhas-filhas não carregam essas informações. A RLS do Base44 avalia campos da própria entidade e não deve depender de uma consulta implícita ao pai.

### Por que não aplicar RLS de proprietário imediatamente

Se as filhas fossem alteradas agora para:

```json
"read": { "created_by_id": "{{user.id}}" }
```

os usuários deixariam de enxergar ingredientes/tags/insumos das receitas e cardápios do catálogo-base, pois essas linhas foram criadas pelo administrador/importação.

Abrir `read` para todos também não é solução definitiva, porque permitiria enumerar linhas de receitas/cardápios pessoais de outros usuários por chamada direta à API.

## Migração necessária para fechar o P0 das filhas

Adicionar às sete entidades-filhas:

```json
"is_base": {
  "type": "boolean"
},
"usuario_dono_id": {
  "type": "string"
}
```

Executar backfill por entidade-pai:

- se pai `is_base === true`: filho `is_base=true`, `usuario_dono_id=null`;
- se pai `is_base === false`: filho `is_base=false`, `usuario_dono_id=parent.usuario_dono_id || parent.created_by_id`.

Depois do backfill, aplicar:

### read

```json
{
  "$or": [
    { "data.is_base": true },
    { "data.usuario_dono_id": "{{user.id}}" },
    { "user_condition": { "role": "admin" } }
  ]
}
```

### update/delete

```json
{
  "$or": [
    { "data.usuario_dono_id": "{{user.id}}" },
    { "user_condition": { "role": "admin" } }
  ]
}
```

### create

A criação pelo usuário deve sempre preencher `is_base=false` e `usuario_dono_id={{user.id}}`. A criação de linhas-base deve ocorrer somente como admin.

## Código que precisa acompanhar a migração

Os helpers de fork atuais:

- `src/lib/forkReceita.js`
- `src/lib/forkCardapio.js`

já identificam o usuário dono no pai, porém ao copiar as linhas-filhas ainda não propagam `is_base=false` e `usuario_dono_id`.

Além dos forks, todos os pontos de criação de linhas-filhas em telas de edição precisam gravar a mesma propriedade. A RLS só deve ser fechada depois do backfill e dessa propagação para evitar indisponibilidade de dados.

## Situação do P0 — concluída em 2026-08-22

- Escrita indevida em catálogo global: **FECHADA**.
- Isolamento de Planejamento, ListaCompras e PerCapitaUsuario: **FECHADO**.
- Logs/configurações sensíveis auditados: **FECHADO ou já protegido**.
- Migração de propriedade das sete entidades-filhas: **CONCLUÍDA**.
- RLS definitiva das sete entidades-filhas: **ATIVA NO BASE44**.
- Propagação de propriedade em novos registros-filhos: **CENTRALIZADA EM `src/lib/secureChildEntities.js`**.

### Resultado da migração das filhas

Foram adicionados `is_base` e `usuario_dono_id` a:

- `IngredienteReceita`
- `ReceitaTag`
- `InsumoReceita`
- `IngredienteEsquecidoReceita`
- `CardapioReceita`
- `CardapioInsumo`
- `CardapioTag`

O backfill classificou os registros existentes pelo pai. Uma receita criada por usuário comum que estava indevidamente marcada como `is_base=true` (`BISCOITO DE CHOCOLATE`) foi normalizada para receita pessoal. Também foi preenchido `usuario_dono_id` em uma receita pessoal antiga que estava sem proprietário explícito.

Após o backfill, uma consulta de invariantes nas sete entidades retornou **zero registros** sem `is_base` e **zero registros privados** sem `usuario_dono_id`.

### RLS definitiva aplicada

- `create`: admin, ou usuário criando linha privada com `is_base=false` e `usuario_dono_id={{user.id}}`;
- `read`: linha-base, linha do próprio usuário ou admin;
- `update/delete`: somente proprietário ou admin.

Todos os 39 pontos de criação frontend das sete entidades foram direcionados para `src/lib/secureChildEntities.js`, que herda a classificação da entidade-pai antes do `create`.

### Validação Usuário A × Usuário B

Foi adicionado `scripts/test-rls-children.mjs`, que lê as regras reais dos sete schemas e valida automaticamente a matriz A × B:

1. A e B leem linhas-base;
2. A lê/atualiza/exclui sua linha privada;
3. B não lê, atualiza nem exclui linha privada de A;
4. A não lê linha privada de B;
5. usuário comum não cria linha-base;
6. usuário comum não cria linha declarando outro usuário como dono;
7. admin mantém acesso total.

Execução em 2026-08-22: **OK — 7/7 entidades aprovadas**.

Limitação operacional registrada: a integração administrativa disponível não permite impersonar duas sessões de usuários existentes, e novo cadastro por senha exige OTP por e-mail. Por isso, a validação cruzada automatizada foi combinada com consultas de invariantes diretamente no banco real. Um smoke test manual com duas sessões reais continua recomendado antes do go-live, junto ao Security Check do Base44.

# Estado consolidado da revisão de segurança — 2026-08-22

Esta seção supersede os estados intermediários e itens marcados como “pendentes” nas etapas anteriores deste documento.

## P0 — encerrados

### 1. Tokens de autenticação em logs

- O diagnóstico temporário que enviava a URL completa para `LogUserAgentDiagnostico` foi desativado.
- `access_token` é removido da URL antes do carregamento dos scripts externos/aplicação.
- O endpoint legado retorna `410` e não grava dados.
- 116 registros históricos de `LogUserAgentDiagnostico` tiveram `url_acessada` e `user_agent` removidos sem leitura dos valores.
- Registros históricos de pagamento que continham a chave `token` em payload/erro foram saneados.

**Estado:** FECHADO.

### 2. Elevação de privilégio e autoativação de assinatura

O schema `User` passou a restringir escrita a administradores nos campos:

- `role`;
- `plano_atual`;
- `status_assinatura`;
- `data_inicio`;
- `data_expiracao`;
- `data_proxima_cobranca`;
- `ciclo_renovacao`.

`anotacoes_admin` possui leitura e escrita exclusivas de admin.

O usuário continua podendo editar apenas seus dados legítimos de perfil e faturamento, como nome, telefone, empresa, CPF/CNPJ e endereço.

**Estado:** FECHADO.

### 3. Conteúdo privado × catálogo compartilhado

`Receita` e `Cardapio` foram endurecidos na raiz, além das sete entidades-filhas já migradas:

- `is_base` agora tem `default=false`;
- `is_base` possui escrita exclusiva de admin;
- `create` aceita somente:
  - admin; ou
  - registro privado com `is_base=false` e `usuario_dono_id={{user.id}}`.

Todos os pontos de criação frontend de Receita/Cardápio foram centralizados em `src/lib/secureRootEntities.js`.

Consequências:

- usuário comum não cria conteúdo diretamente no catálogo compartilhado;
- usuário comum não promove sua cópia pessoal para `is_base=true` por `update`;
- catálogo-base passa a ser decisão administrativa explícita.

**Estado:** FECHADO.

### 4. Histórico de alterações manipulável

`HistoricoAlteracaoReceita` foi transformado em log imutável:

- frontend chama `registrarHistoricoReceita`;
- function autentica o usuário;
- confirma que ele realmente pode editar a receita indicada;
- usa o nome real da receita, não um nome fornecido pelo cliente;
- limita e normaliza a lista de campos alterados;
- grava via `asServiceRole` com `usuario_id` explícito;
- usuário titular pode ler o próprio histórico, mas não criar, editar ou apagar entradas diretamente;
- admin mantém acesso administrativo.

**Estado:** FECHADO.

- `/admin/*`;
- `/auditorias`;

### 6. Assinatura/entitlement

`ProtectedRoute` aplica avaliação central de assinatura e permite apenas rotas necessárias para recuperação/renovação, como Planos, Conta e Suporte.

Funções de IA voltadas ao cliente usam `exigirAssinaturaAtiva` no backend, evitando bypass por chamada direta à function.

**Estado:** FECHADO para os fluxos auditados.

### 7. Importadores CSV / SSRF

Os importadores usam `base44/shared/fetchCsvSeguro.ts`.

A política atual aceita apenas:

- `https:`;
- host exato `base44.app`;
- porta padrão/443;
- caminho pertencente ao app atual: `/api/apps/6a2b263c4c1cb1e47d54d8b7/files/`;
- no máximo 3 redirects, todos revalidados pela mesma allowlist;
- timeout de 10 segundos;
- limite máximo de 5 MB.

A origem permitida foi confirmada a partir de URLs reais produzidas pelo `UploadFile` deste aplicativo.

Isso elimina fetch arbitrário de hostname externo e o vetor de DNS rebinding presente em uma validação baseada apenas em IP literal.

**Estado:** FECHADO.

### 8. Configuração global misturada com preferência pessoal

A chave global `auto_update_prices` foi retirada de `AppConfig` e migrada para `ConfiguracaoSistema`, entidade admin-only.

`AppConfig` permanece para configurações pessoais do usuário, como dados da empresa e preferências individuais.

**Estado:** FECHADO.

### 9. Aceite de Termos

Os campos `termos_aceitos_em` e `termos_versao_aceita` não são mais gravados diretamente pelo browser.

- `registrarAceiteTermos` grava o primeiro aceite via backend/service role;
- os dois campos têm escrita direta restrita a admin;
- cadastro por e-mail exige checkbox e registra o aceite após autenticação;
- cadastro via Google também exige checkbox antes do OAuth;
- o retorno OAuth utiliza um marcador efêmero em `sessionStorage` e grava o aceite no backend somente após existir sessão autenticada.

**Estado:** FECHADO para os fluxos de cadastro auditados.

## Pagamentos e comunicações

### Mercado Pago

- preço é obtido da configuração server-side, não do valor enviado pelo cliente;
- HMAC do webhook é validado;
- comparação do digest é feita em tempo constante;
- após a assinatura, order/payment é consultado novamente na API do Mercado Pago;

- `LogWhatsapp` permanece admin-only e registra apenas metadados necessários ao acompanhamento do envio.

**Estado:** ENDURECIDO.

## Functions agendadas — risco arquitetural residual controlado

A documentação Base44 informa que toda backend function possui endpoint HTTP próprio e que uma chamada HTTP direta não carrega usuário autenticado por padrão. Functions disparadas por automação precisam, ao mesmo tempo, funcionar sem `auth.me()`.

Por isso, funções agendadas não foram artificialmente protegidas com `role=admin`, o que quebraria o scheduler.

Mitigações implantadas:

- avisos de trial/plano: idempotência diária por destinatário/tipo;
- lembrete de pagamento pendente: flag própria de processamento único;
- atualização automática de preços: configuração global admin-only + cooldown de 20 horas;
- webhook Mercado Pago: HMAC + reconsulta ao provedor + idempotência.

**Estado:** RISCO RESIDUAL DE PLATAFORMA, COM IMPACTO LIMITADO NO CÓDIGO DO APP.

## Bootstrap por URL — risco residual não comprovado

`app-params.js` ainda reconhece parâmetros de bootstrap usados pelo ecossistema Base44, inclusive `functions_version`.

Foi confirmado no bundle que:

- `serverUrl` é same-origin (`''`), portanto `app_base_url` não reponta as APIs de entidades para um host arbitrário no fluxo atual;
- `functions_version` é encaminhado pelo SDK como versão de functions e o bundle atual usa `preview` por padrão;
- retornos de login/OAuth já removem `access_token`, `app_id`, `app_base_url`, `functions_version` e `from_url` de URLs de retorno não confiáveis.

A documentação pública consultada em 2026-08-22 descreve preview, versões e publicação, mas não documenta o contrato interno do header de versão de functions. Por isso, remover ou bloquear `functions_version` sem um sinal oficial poderia quebrar o editor/preview do Base44.

**Estado:** NÃO EXPLORADO/COMPROVADO; NÃO ALTERADO POR SEGURANÇA OPERACIONAL.

### Limitação do build nesta etapa

O shell retornado pela ferramenta de sandbox Base44 passou a abrir `/workspace` sem o checkout do projeto e sem `package.json`. Portanto o `npm run build` final não pôde ser repetido depois das últimas alterações. Um build anterior, antes deste último conjunto de endurecimentos, havia concluído normalmente.

Essa falha operacional do sandbox **não equivale a falha de compilação do código**, mas também não deve ser tratada como evidência de build final aprovado.

5. reavaliar `functions_version` caso o Base44 publique contrato oficial para versões de functions ou permita restringir o header em produção.
