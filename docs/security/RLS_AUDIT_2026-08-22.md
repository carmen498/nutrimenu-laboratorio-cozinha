# Auditoria P0 — Row Level Security (RLS)

Data: 2026-08-22
Escopo: entidades Base44 do Laboratório de Cozinha

## Objetivo

Garantir que:

1. dados pessoais de um usuário não sejam lidos, alterados ou excluídos por outro usuário;
2. catálogos globais sejam legíveis pelos clientes, mas somente administradores possam alterá-los;
3. dados administrativos, logs e configurações não sejam expostos a usuários comuns;
4. entidades-filhas de receitas e cardápios respeitem a mesma propriedade da entidade-pai.

## Padrões adotados

### Dados pessoais

- create: usuário autenticado ou admin;
- read/update/delete: `created_by_id == {{user.id}}` ou admin.

### Catálogos globais

- read: liberado;
- create/update/delete: somente `role=admin`.

### Dados administrativos/logs

- read/create/update/delete: somente `role=admin`.

## P0 pendente — entidades-filhas mistas

As seguintes entidades não podem receber simplesmente `created_by_id == user.id`, porque armazenam tanto linhas pertencentes ao catálogo-base quanto linhas de cópias pessoais:

### Filhas de Receita

- `IngredienteReceita`
- `ReceitaTag`
- `InsumoReceita`
- `IngredienteEsquecidoReceita`

### Filhas de Cardápio

- `CardapioReceita`
- `CardapioInsumo`
- `CardapioTag`

O pai (`Receita`/`Cardapio`) já possui `is_base` e `usuario_dono_id`, mas as linhas-filhas não carregam essas informações. A RLS do Base44 avalia campos da própria entidade e não deve depender de uma consulta implícita ao pai.

### Por que não aplicar RLS de proprietário imediatamente

Se as filhas fossem alteradas agora para:

```json
"read": { "created_by_id": "{{user.id}}" }
```

os usuários deixariam de enxergar ingredientes/tags/insumos das receitas e cardápios do catálogo-base, pois essas linhas foram criadas pelo administrador/importação.

Abrir `read` para todos também não é solução definitiva, porque permitiria enumerar linhas de receitas/cardápios pessoais de outros usuários por chamada direta à API.

## Migração necessária para fechar o P0 das filhas

Adicionar às sete entidades-filhas:

```json
"is_base": {
  "type": "boolean"
},
"usuario_dono_id": {
  "type": "string"
}
```

Executar backfill por entidade-pai:

- se pai `is_base === true`: filho `is_base=true`, `usuario_dono_id=null`;
- se pai `is_base === false`: filho `is_base=false`, `usuario_dono_id=parent.usuario_dono_id || parent.created_by_id`.

Depois do backfill, aplicar:

### read

```json
{
  "$or": [
    { "data.is_base": true },
    { "data.usuario_dono_id": "{{user.id}}" },
    { "user_condition": { "role": "admin" } }
  ]
}
```

### update/delete

```json
{
  "$or": [
    { "data.usuario_dono_id": "{{user.id}}" },
    { "user_condition": { "role": "admin" } }
  ]
}
```

### create

A criação pelo usuário deve sempre preencher `is_base=false` e `usuario_dono_id={{user.id}}`. A criação de linhas-base deve ocorrer somente como admin.

## Código que precisa acompanhar a migração

Os helpers de fork atuais:

- `src/lib/forkReceita.js`
- `src/lib/forkCardapio.js`

já identificam o usuário dono no pai, porém ao copiar as linhas-filhas ainda não propagam `is_base=false` e `usuario_dono_id`.

Além dos forks, todos os pontos de criação de linhas-filhas em telas de edição precisam gravar a mesma propriedade. A RLS só deve ser fechada depois do backfill e dessa propagação para evitar indisponibilidade de dados.

## Situação do P0 — concluída em 2026-08-22

- Escrita indevida em catálogo global: **FECHADA**.
- Isolamento de Planejamento, ListaCompras e PerCapitaUsuario: **FECHADO**.
- Logs/configurações sensíveis auditados: **FECHADO ou já protegido**.
- Migração de propriedade das sete entidades-filhas: **CONCLUÍDA**.
- RLS definitiva das sete entidades-filhas: **ATIVA NO BASE44**.
- Propagação de propriedade em novos registros-filhos: **CENTRALIZADA EM `src/lib/secureChildEntities.js`**.

### Resultado da migração das filhas

Foram adicionados `is_base` e `usuario_dono_id` a:

- `IngredienteReceita`
- `ReceitaTag`
- `InsumoReceita`
- `IngredienteEsquecidoReceita`
- `CardapioReceita`
- `CardapioInsumo`
- `CardapioTag`

O backfill classificou os registros existentes pelo pai. Uma receita criada por usuário comum que estava indevidamente marcada como `is_base=true` (`BISCOITO DE CHOCOLATE`) foi normalizada para receita pessoal. Também foi preenchido `usuario_dono_id` em uma receita pessoal antiga que estava sem proprietário explícito.

Após o backfill, uma consulta de invariantes nas sete entidades retornou **zero registros** sem `is_base` e **zero registros privados** sem `usuario_dono_id`.

### RLS definitiva aplicada

- `create`: admin, ou usuário criando linha privada com `is_base=false` e `usuario_dono_id={{user.id}}`;
- `read`: linha-base, linha do próprio usuário ou admin;
- `update/delete`: somente proprietário ou admin.

Todos os 39 pontos de criação frontend das sete entidades foram direcionados para `src/lib/secureChildEntities.js`, que herda a classificação da entidade-pai antes do `create`.

### Validação Usuário A × Usuário B

Foi adicionado `scripts/test-rls-children.mjs`, que lê as regras reais dos sete schemas e valida automaticamente a matriz A × B:

1. A e B leem linhas-base;
2. A lê/atualiza/exclui sua linha privada;
3. B não lê, atualiza nem exclui linha privada de A;
4. A não lê linha privada de B;
5. usuário comum não cria linha-base;
6. usuário comum não cria linha declarando outro usuário como dono;
7. admin mantém acesso total.

Execução em 2026-08-22: **OK — 7/7 entidades aprovadas**.

Limitação operacional registrada: a integração administrativa disponível não permite impersonar duas sessões de usuários existentes, e novo cadastro por senha exige OTP por e-mail. Por isso, a validação cruzada automatizada foi combinada com consultas de invariantes diretamente no banco real. Um smoke test manual com duas sessões reais continua recomendado antes do go-live, junto ao Security Check do Base44.
